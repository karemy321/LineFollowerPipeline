What's new in this version (v2)

  • Distractor rejection. A dark chair leg, a bag, a shadow or the dark floor past a table edge is no longer taken for the line: a band only counts as the line if its width and line-ness match the line measured at calibration (rejectDistractors, bandMaxWidthMult, bandMinWidthMult).
  • Steering uses the whole ⊥. Steering = offset of the line in the scan strip (as before) + heading of the line from the look-ahead (new). A robot at an angle to the line now gets a steering value (±15° → ≈ ±8, ±30° → ≈ ±17). Range -50 … +50 and sign are unchanged.
  • Hidden line is held. A line that disappears mid-image is held for up to 6 frames (trackHoldFrames) instead of kicking steering to ±50 at once.
  • Steadier lock. The gate follows the predicted line position and can no longer grow to the whole frame; a valid-looking lock is not stolen by a nearby object.
  • Richer callback. FrameData adds steerOffsetTerm, steerHeadingTerm, headingDeg, headingConfidence, lineHeld, rejectedBands.
  • No API break. Nothing was removed or renamed — existing integration code compiles and runs unchanged.

What This Library Does

LineFollowerPipeline.java is a pure-Java, zero-dependency line-following vision processor. You feed it raw camera frames — grayscale, YUV 4:2:0 or ARGB — and it returns two integer control values your robot can act on directly: a steering direction and a speed/tracking signal. No OpenCV, no Android APIs, and no native libraries are required.

Requirements

  • Java 8 or higher
  • One file only: LineFollowerPipeline.java
  • No external dependencies

Have colour frames? Use calibrateYuv420(y, u, v, w, h) / processFrameYuv420(…) (Android camera) or calibrateArgb(…) / processFrameArgb(…) instead — colour input separates even line/floor colours of the same brightness. See Input Formats.

Calibration is required. processFrame() must not be called until calibrate() has returned true. The robot must be correctly placed on the line — straight, on a straight section, with floor visible on both sides — while calibrating. See Calibration below.

Input Formats

Each format has a matching calibrate / process pair. Use the same format for both.

Important: all arrays must be packed with no row padding (and the U/V planes with no pixel interleaving). Android CameraX planes are padded / interleaved — strip that before passing the data in (see copyLumaPlane / copyChromaPlane in RoboPhoneApp's MainActivity). Arrays that are too short throw IllegalArgumentException.

Which format should I use?

  • Colour (YUV / ARGB) separates any two colours that look different — even two colours of the same brightness (e.g. red on green).
  • Grayscale works for any two colours that differ in brightness (white on black, black on blue, white on brown, black on white). Calibration reports ISSUE_LOW_CONTRAST and keeps retrying if the two colours have the same brightness.

Output Format

processFrame() returns a reused int[2] array. Copy the values immediately if you need to keep them — the same array is overwritten on the next call.

Track Memory

When searching for the line (start-up, or after it was lost), the pipeline no longer simply takes the biggest band in view: it prefers the band nearest the calibrated straight-ahead column whose width matches the line width measured during calibration. While the locked line is lost at the frame edge, steering reads ±50 toward the side it left; a line that vanishes mid-image is held first (see When the Line Is Lost or Hidden).

Distractor Rejection (chair, bag, shadow, table edge) NEW

Objects with a colour close to the line's (a black chair leg on a black-tape track, a shadow on wood, the dark floor beyond a table edge) pass the threshold exactly like the line. With rejectDistractors on, a band only counts as the line if it looks like the line learned at calibration:

  • Width — the band must be between bandMinWidthMult × and bandMaxWidthMult × the calibrated line width (the maximum is corrected for the line's slant in the image). Wide blobs, dark regions at the frame edge and thin specks are rejected.
  • Line-ness — among acceptable bands, the one whose pixels are as line-like as the calibrated line wins (a shadow on wood only just passes the threshold; the tape is well past it).
  • Continuity — while locked, the band nearest the predicted position wins (on the scale of one line width), and a band that is the line merged with a blob or shadow is cut back to the part that continues the line (its strong core, or the edge that sits where the line's edge was).
  • Look-ahead — the row-by-row tracker of the V-ROI applies the same width test on every row (perspective-scaled), so it cannot step onto a nearby object; a run cut by the scan window is only used through the edge that continues the line.
  • Hidden line — if the locked line disappears in the middle of the image (glare, a shadow or an object over it) the last steering and tracking are held for trackHoldFrames; a line that leaves at the frame edge (a real turn) is still pinned to that edge at once.
  • Relock — the lock correction (trackRelockFrames) still exists, but a valid-looking locked line is only abandoned after three times as many frames, so a chair leg near the centre cannot steal the lock during a turn.

What you must ensure — the rules compare everything with the line measured at calibration, so:

  • Calibrate with the robot on the line, straight, on a straight section, with floor visible on both sides, and no distractor inside the scan strip during calibration.
  • Use one tape width for the whole track (a reasonable width: the line should cover well under half of the scan strip). Width changes of more than about 2× (bandMaxWidthMult) or less than 0.3× (bandMinWidthMult) are treated as "not the line". Recalibrate when you change tape.
  • Set cameraTiltDeg / verticalFovDeg close to the real camera — the look-ahead width test uses them.
  • Remaining limit: a dark object of exactly the tape's width, lying where the line is predicted to be, can still be taken for the line.

Steering from the Whole ⊥ (offset + heading) NEW

The pipeline looks at the line as a ⊥ (an inverted "T"): the base is the horizontal scan strip (H-ROI), the vertical part is the line followed up the look-ahead (V-ROI). The v1 steering used only the base of the ⊥ — where the line crosses the scan strip — so a robot at 30° to the line and a robot straight on it read the same value if the line crossed the strip at the same point. The steering now also uses the line's heading from the vertical part of the ⊥:

  • W is the frame width in pixels; the centroid is where the line crosses the scan strip; the calibrated column is the straight-ahead column measured during calibration (FrameData.steerRefXFrac).
  • ψ is the direction of the line on the floor where it crosses the scan strip: the H-ROI centroid and the look-ahead rows on the line are projected onto the floor with the camera geometry (cameraTiltDeg, verticalFovDeg, exact pinhole model) and fitted with a parabola; its tangent at the strip is ψ. Positive = the line heads to the right.
  • ψ₀ is the heading measured during calibration (phone yaw on its mount), so a robot correctly placed on a straight line still reads 0. Calibrate on a straight section; a calibration heading larger than steerHeadingCalibMaxDeg is ignored (ψ₀ = 0).
  • Together the two parts are the lateral position of a pure-pursuit target point a distance L further along the line, in the same units as the v1 steering.
  • c (the heading confidence, FrameData.headingConfidence, 0 … 1) fades the heading out when too little of the line is visible ahead (end of line, line leaving the frame) or when the line is not a smooth curve (a 90° corner, a junction) — the steering then falls back to the v1 offset only.
  • Signs: both parts are positive when the robot must turn right (line to the right / line heading right). FrameData.steerOffsetTerm and steerHeadingTerm are the two weighted parts in output units (already halved), so before clamping and rounding steering ≈ steerOffsetTerm + steerHeadingTerm.

Sensitivity & Tracking

Tracking Minimum Value

By default Tracking never reaches zero: result[1] is clamped to a floor of 5, so the robot always receives at least a small speed signal. This prevents mechanical problems caused by a complete stop command.

Calibration Frames

Calibration

Before calling processFrame() you must calibrate. Place the robot correctly on the line, then call calibrate() (or the YUV / ARGB version) once per camera frame until it returns true:

Calibration has two phases:

  1. Learn the colours (colorCalibFrames, default 5 frames). The scan strip is sampled and split into two colour clusters (k-means). The floor is the cluster that fills both the left and right frame edges; the other is the line. If that fails — typically a shadow or uneven light making part of the floor almost as dark as a dark line — 3 and then 4 clusters are tried: the line is the cluster that forms one band and never reaches the frame edges, and all other clusters (lit floor, shadowed floor…) count as floor. A Fisher linear discriminant then gives the colour direction that best separates line from floor, and every later frame is converted to a "line-ness" image (line bright, floor dark) before the usual Otsu + line-lock processing. Skipped when autoColor = false or when the colours were given with setTrackColors().
  2. Find straight-ahead CHANGED Collects calibFrames (default 10) solid line detections — preferring the band where colour learning saw the line and, with rejectDistractors, of the width colour learning measured — and takes their median as: the steering zero reference (straight-ahead column); the typical line width and line-ness level (used by distractor rejection); and the heading zero ψ₀ (only when steerHeadingWeight ≠ 0): the median line heading of the frames that saw enough look-ahead. It is used only if at least half of the frames saw it and it is within steerHeadingCalibMaxDeg; otherwise ψ₀ = 0.

With the defaults calibration needs at least 15 frames (5 + 10). It returns true once both phases are done. Progress and problems are reported in the callback (calibPhase, calibProgress, calibIssue):

Before you calibrate — checklist NEW

  • The robot stands on the line, straight, on a straight section (the heading zero is learned here).
  • The line is inside the scan strip, near the middle, with floor visible on both sides (both frame edges must show floor).
  • No chair leg, bag, shadow edge or second tape inside the scan strip.
  • The tape width is the one used on the whole track.

If calibration cannot complete, calibrate() simply keeps returning false — there is no timeout. Show calibIssue to the user, fix the cause (see the table) and keep feeding frames; call requestRecalibration() to start again from phase 1. Do not drive on processFrame() output before calibration is done: until then the steering zero is the image centre, there is no calibrated line width (so distractor rejection cannot work), and if the colours were not learned yet the frame is read as plain brightness with trackIsBright polarity.

Giving the colours yourself (optional)

setTrackColors() has no effect when autoColor = false, and throws IllegalArgumentException if the two colours are the same.

Re-calibrating mid-run

Recalibrate whenever you move to a track with different colours, very different lighting or a different tape width.

When the Line Is Lost or Hidden NEW

Use trackFound (not tracking == 5) to show "TRACK LOST" — a hard turn also reads 5. With trackMemory = false there is no lock, no pinning and no hold: a missing line keeps the steering of its last position and tracking drops to the minimum. If calibration has not completed, see If calibration cannot complete above.

Frame Callback — Overlay Geometry

Register a single callback once, and the library calls it automatically on every calibration frame and every processFrame() frame, passing a FrameData object with everything needed to draw a visual overlay and a status display: the H-ROI strip, the V-ROI look-ahead band, the dynamic road path, the live centroid, calibration progress and the learned colours.

No extra computation is added. The data already exists inside the pipeline — the callback just packages and delivers it (≈ 0.02 ms per frame). The callback runs on the thread that called calibrate / processFrame.

Important: the same FrameData instance is reused on every call. Copy any fields you need to keep beyond the current frame.

Notes

  • The pipeline is not thread-safe. Call calibrate() / processFrame() (and requestRecalibration()) from a single thread only — e.g. have a UI button set a flag that the camera thread checks.
  • The returned int[] is reused on every call. Copy the values if you need them past the next frame.
  • Calibration assumes the robot is correctly placed on the line, with floor visible on both sides. If it is not, call requestRecalibration() once it is repositioned, then calibrate again. Recalibrate whenever you move to a track with different colours, different lighting or a different tape width.
  • A line that jumps sideways by more than the line-lock gate in a single frame (trackMemoryGateMult × line width, around the line's predicted position) is treated as leaving the line — this is what makes the lock ignore reflections.
  • The heading part of the steering relies on cameraTiltDeg and verticalFovDeg matching the real camera. The Android app runs at 960 × 1280 (CameraX picks 1280 × 960, rotated to portrait).
  • Very harsh scenes can still defeat colour learning: e.g. a dark floor in deep shadow, with strong texture, where the tape is only ~10 grey-levels darker than the shadowed floor. Even lighting helps.
  • Performance: ≈ 0.9 ms per frame in YUV colour mode at 960 × 1280 on a desktop CPU (several times more on a phone, still far below the 16.7 ms of 60 Hz); all per-frame buffers are pre-allocated (no garbage per frame, in all three input formats).

RoboPhoneApp — Android Reference Integration

RoboPhoneApp/ runs the library live on the phone camera (CameraX → packed YUV 4:2:0 → calibrateYuv420 / processFrameYuv420). Everything on screen comes from the FrameCallback:

  • Overlay — cyan STEER strip with the detected line, magenta look-ahead band that bends along the line, dashed calibrated straight-ahead line, red ignored robot-body band; mapped with the preview's FILL_CENTER crop so it lines up with the camera image.
  • HUD — STEER bar (−50…+50), TRACK bar (min…100 %), status (calibration progress and problems / TRACKING / TRACK LOST), FPS, learned LINE and FLOOR colour swatches, threshold and colour separation. The app does not show the new v2 FrameData fields yet.
  • RECALIBRATE button — re-learns the colours and the straight-ahead reference (place the robot on the line first).

The app builds the library from source through a Gradle composite build (includeBuild("../LineFollowerLibrary")), so library changes show up in the app on the next build — no jar copying. Library tests: cd LineFollowerLibrary && gradlew test (format / colour unit tests plus camera-simulator scenes: shadows, wood grain, turns, line loss, distractor tapes, dead ends).

Unit tests and v2: with the v2 defaults 8 of the 24 unit tests fail: 7 expect the v1 offset-only steering value (19 for a line 60 px right; v2 reads 22 because the heading part is added) and lostLineReportsTrackLost expects tracking 5 on the first blank frame (v2 holds the last value). They all pass with steerHeadingWeight = 0 and trackHoldFrames = 0. The test expectations still have to be updated for v2. gradlew jar and the app build do not run the tests.
